# 04 - Platform direction (what we are building toward)

Source: plan pages (`plan/sheets`: Overview, Roadmap, Instructions, Lessons) and owner decisions. Read before touching metadata, forms, workflow, licensing, deployment, demo or versioning. The plan is authoritative; this is the working summary.

## 1. Product

PEMS: enterprise engineering and maintenance platform for oil, gas and petrochemical projects (EDMS/VDR, CMMS/EAM, permit to work, inventory/procurement, production, reliability, workflows, local AI). .NET 10, ASP.NET Core MVC/Razor, EF Core 10, SQL Server, Hangfire, SignalR, QuestPDF, Fido2, Serilog, Ollama/Tesseract. Persian-first (RTL, Jalali).

Direction (owner, 2026-10-15/18): turn static MVC modules into a **dynamic BPMS** - users create forms, modules and workflows without code or deploy - on a native .NET engine. Priority: **commercialisation + dynamicisation**, milestones M0..M6 in the Roadmap.

## 6. Licensing in the code (SCRUM-26, 2026-10-26)

- One engine: `PEMS.Licensing` (`LicenseManager`). Product wiring in `PEMS.Web/Licensing`; customer page `Admin/License`; vendor tool `tools/PemsVendorTool` (never referenced by `PEMS.Web`; a test enforces it). Design and map: [LICENSING_TECHNICAL_DESIGN.md](../design/LICENSING_TECHNICAL_DESIGN.md) section 14.
- **`Licensing__Enforce=false` in every `env/*.env` until the owner switches an environment on.** With false nothing is checked, blocked or written, so merging `main` never changes a developer machine. Do not add a second switch, a dev shortcut or a bypass symbol; to try the flow locally set `Licensing__Enforce=true` in your own environment variables, not in the committed file.
- Allowlist of always-free surfaces: `PEMS.Web/Licensing/LicenceFreeSurfaces.cs`, the only place; a new always-free route needs the owner's agreement.
- New licensing behaviour goes through `LicenseManager`; no check outside it. Licence/request/seal formats change only with a version bump and test vectors (design 5.4).
- The signing private key and the reset key never exist in the repository or on CI; tests generate throw-away keys in temp folders. The product contains no signing code.

## 7. Definition-only model (owner decision 2026-11-19, sprint 2 goal)

**The goal:** adding, removing or editing any form, page, menu, action, data source or permission needs **no code change, no build and no deploy**: only database rows, applied by the migrator (install, update, feed, refeed packages; SCRUM-581 to 585, designers SCRUM-603 to 610).

- **Everything is generic and reusable.** One host per kind (`/p` page, `/f` form, `/a` action, `/d` data, file result) plus one route table in the database (SCRUM-768). A module differs from another only by **inputs**: slug, fields, components, authorizations, workflow, data sources. A new per-entity controller, view, handler or inline script is a defect (the ratchet gate SCRUM-611 fails it).
- **Who owns a field or a row** (owner decision 2026-11-06, SCRUM-515, 448): a form field is **platform** (ours: delivered and changed only by product updates, read-only for the customer, `owner: "platform"`) or **application** (the customer's, the default: editable by them, never touched by an update). The customer's data and application fields always win: an update merges the new platform fields into a customised form, keeps every application field as it is, and **stops before changing anything** with a report (form, field, reason) when it would collide with or retype an application field. A customised definition keeps its version; the new shipped version is kept beside it and `GET /api/v1/definitions/{id}/upstream` shows the difference; reset to shipped republishes the shipped payload. The words are "platform" and "application" ("business" and "system" are not used). Code: `FormOwnership`, `DefinitionService.ShipAsync`. Decision record: [ADR-0016](../../plan/adr/0016-field-ownership-platform-and-application.md); the platform fields today are the `code` field of the seven master-data forms (departments, disciplines, maintenance groups, material categories, storage locations, units of measure, warehouses).
- **The ratchet gate** (SCRUM-611): `DefinitionRatchetTests` compares every Razor view and the action count of every controller with `plan/sheets/definition-ratchet.json` and fails with the file or controller that is new; a host or static controller (`plan/sheets/classification.json`) is exempt. A new screen is a page or form definition, a new read or write is a data source or action definition. If code really is the right answer, run the test once with `PEMS_WRITE_RATCHET=1` and say why in the pull request: the baseline diff is what the reviewer reads. A conversion only lowers the numbers: after deleting the controller and its views run `PEMS_WRITE_CLASSIFICATION=1 PEMS_WRITE_RATCHET=1 dotnet test PEMS.Tests --no-build --filter "FullyQualifiedName~.ClassificationClosureTests.|FullyQualifiedName~.DefinitionRatchetTests."` once: the classification table gets a `converted` receipt for the deleted type and the ratchet baseline drops (without it `ClassificationClosureTests` fails with "in the table as pending but no such type exists").
- **Measure before you cache** (SCRUM-577): every page and form request logs one line with the trace id, the time of each stage (resolve, authorize, hydrate, evaluate, render) and the counts (definitions, hydrators, option lists, options, rows); a stage over its budget (`Definitions__Budgets__*Ms` in `env/*.env`) logs a warning with the same trace id. The caches of SCRUM-574 to 576 are only added where these numbers show the need.
- **One action, several writes, a confirmation** (SCRUM-593, 594, 595): an action that writes several tables is ONE action definition with the handler `action.steps` (`steps`: handler key, `parameters`, `as`, `values` with sources `field:name`, `literal:text`, `step:as.key`). The steps run in order inside ONE database transaction; the first refusal or exception rolls everything back and later steps do not run. A handler that returns values (`ActionOutcome.Returned`, the entity create action returns the row it wrote) feeds later steps and the `{as.key}` placeholders of the definition's `redirect`. A handler opens its scope with `ActionScope.Open` (never `scopes.CreateScope()`), so it joins the transaction. An action that needs a security key declares `stepUp: { resource, action }`: the host answers `StepUpRequired` with the challenge (HTTP 428 for a fetch), verifies the answer, audits a denial, and only then runs the operation; a definition that declares it never runs without a verifier. The service no longer checks the WebAuthn answer itself once its action declares `stepUp` (checking twice fails: an answer is single-use).
- **Files in and out** (SCRUM-596, 615): a file that comes in is the action handler `file.upload` (`field`, `profile`: attachment, image, spreadsheet, csv or pdf, `folder`, `maxFileMb`, `required`): the file passes `IUploadGuard` (allow-list, size, content check, malware-scan hook of SCRUM-202) with the profile the definition names, is stored by `IFileStorageService` under a generated name, and its `key`, `fileName`, `size` and `contentType` are returned, so a following step of `action.steps` writes them to a record. The generic hosts carry `[DefinitionUploadPolicy]` (the global upload filter lets the request through; a file no `file.upload` step reads is never saved). A file that goes out is `file.export` (`dataSource` of a grid data source, `format` csv or xlsx, `columns`, `maxRows` up to 50000): read with the rights of the user, a cell that a spreadsheet would run as a formula is written as text, and the host answers with the file. Not generic yet: PDF output and downloading a stored file by key (it needs a record-level authorization decision per file, so it goes with the conversion of the controller that serves the file).
- **Caches of the engine** (SCRUM-574, 575, 576), added after the measurements of SCRUM-577: a definition is compiled into an immutable `RenderPlan` once per content hash (`RenderPlanCache`; a new version replaces it in one step, a version that does not compile keeps the last good plan, every request works on its own copy); hydrated results are shared by the users of one permission set (`HydrationCache`, key = definition hash, sorted roles, culture, scope; a time to live, never a row-level result: a data source provider opts in with `CacheSeconds` only when its options depend on nothing but the roles); the visible items of the sidebar are evaluated once per permission set (60 seconds, cleared when the menu changes), while titles, links and the active item are made per request. A new cache needs its numbers in the log line of SCRUM-577 and a test that two permission sets never share an entry.
- **Reads and the menu as definitions** (SCRUM-592, 590, 373): a list is the grid data source with provider `entity` (fields, search, sort, presets, counts, lookups); an aggregate is the provider `entity-aggregate` (`groupBy`, `measures` with count, sum, avg, min, max, fixed `where`, `maxRows`), same rights and paging as the grid; a single record is read with the record binding of the page engine. The generic entity write actions check a mapped value with the one validator against the `[MaxLength]`, `[StringLength]` and `[Range]` the entity declares. The menu is the definition kind `menu` (`items` with key, parent, kind link, section or subheading, order, title in both languages or a titleKey, icon, `rule`, and for a link exactly one of `page`, `form`, `url`): shipped with the package it is synced into the sidebar table at start-up with the ownership rule of the sidebar (what the product ships is updated, what an administrator changed is never touched, a code default wins over a fed item with the same key), and visibility is the permission rule language of the sidebar (`Perm:Module.Action`, `RoleAction`, `Role`, `Flag`, `Always`, with `&` and `|`).
- **Grants of roles to definitions** (SCRUM-591): the table `DefinitionGrants` (kind, definition key, role name, effect `allow` or `deny`, reason) is registered in the entity catalog, so an administrator lists, adds and removes grants with the generic entity pages and actions, audited by the context's SaveChanges, no deploy. Stage 2 of the pipeline, the action host and the data-source reader ask `IDefinitionAccess.CanOpenAsync(kind, key, permission, roles)`: the code `permission` of the definition stays the floor, an `allow` grant lets a role without it open the definition, a `deny` of any of the user's roles always wins; no grants means the old answer. A grant decides the opening only: the permission, separation-of-duties and scope checks inside an action still apply.
- **Shipped workflows** (SCRUM-517): a workflow the product ships is a JSON document (`module`, `context`, `name`, `stages` with stable `key`s, `transitions` between those keys), read by `ShippedWorkflow.Parse` and shipped by `WorkflowShipper`: a missing workflow is created and published as version 1; an existing one is never overwritten (the customer's published version stays active, running instances finish on their version, versions are immutable); when the document changed (its hash is kept in the version's change summary as `shipped:<hash>`), the new structure is stored as a Draft version marked `upstream-changed` with a diff against the active version, for an administrator to review and publish; with a draft already open nothing is stored. A seeder family is converted by writing its document and a clean-install parity test.
- **Shipped reference data** (SCRUM-516): lookups, templates and numbering schemes the product ships are `reference-data` definitions (`list`, `owner` platform or application, `rows` with a stable `key`, optional row `owner`, `values`), one per list. `ReferenceDataSync.Plan` is the update rule: a missing row is inserted; a platform-owned row the customer did not edit (its values still equal the fingerprint of what the product last wrote) is updated; an application-owned row, an edited row and a row with no record of what the product wrote are never written, a difference is reported as an upstream change; a row the product stops shipping is retired (inactive), never deleted; the customer's own rows are never touched. Moving a list needs an applier for its table and the owner's confirmation of its default owner; the table of lists and owners is kept with the definitions.
- **One field-error shape** (SCRUM-380): `ApiFieldError` (pointer as JSON pointer, stable constraint code, message key, message in the user's language, params) is the shape of the API problem (422), the validator (`ValidationMessages.ToApiErrors`), a refused form or grid action posted for JSON (`errors` next to the older `error` text, via `ErrorShape.FromOutcome`) and an import cell (`ErrorShape.ImportCell`, pointer `/rows/{row}/{field}`). A module that reports errors another way fails `ErrorShapeTests`.
- **Files out by definition** (SCRUM-615): `file.export` (CSV or Excel of a grid data source) and `file.download` (a stored file by the key an upload returned, only inside the `prefix` folder the definition names, with the action's own permission and roles; a record-level rule is a `deny` rule or a data source on the record) return a file through `ActionOutcome.Download`; the host sends it. PDF output is not built yet (the library and its licence are an owner decision).
- **Which shipped form fields are platform-owned** (owner decision 2026-11-19, SCRUM-515): only system fields (the on/off and default switches, module and routing targets, storage provider, permission pairs of separation of duties; later ids, status, audit and workflow fields) carry `"owner": "platform"` in the shipped form definitions; business fields (names, descriptions, lookups such as the discipline) stay with the customer. A new shipped form marks its system fields the same way.
- **Text pages are a definition** (batch 5, SCRUM-733): the page engine input `content-blocks` (registered component, options `blocks`: heading, text, alert, list, code, link, divider; every text in both languages, escaped, links only to paths of this site) renders a page that only shows text, as one instance in a region of a layout; a controller that only returned such a view is converted by a page definition plus a `route` definition for the old address, the menu entry pointing at `/p/<key>`, the controller, view, classification row and ratchet entries deleted.
- **Link hubs are a definition** (batch 5, SCRUM-748): the `content-blocks` block `cards` (Columns 1, 2, 3, 4 or 6; each card an icon `bi-...`, title, text and `links` to paths of this site) draws a hub of links such as Settings; a part of a page for some roles only is an instance with a `visible` expression (`'SystemAdmin' in user.roles or ...`), so the role rule stays in the definition. A controller and view that only showed such a hub are replaced by the page and a `route` definition per old address.
- **Search text as an operation argument** (batch 5, SCRUM-712): a grid data source over a read operation can take the text typed in the quick search of the grid as the argument `param:search` (a semantic or full-text search of a service); the rows are then not filtered again by their text. The semantic search page is `/p/knowledge-base` over the operation `KnowledgeBase.Search`; an unreferenced developer smoke-test endpoint (`/AI/Test`, SCRUM-666) is deleted, not converted.
- **Spreadsheet import by definition** (batch 5, SCRUM-681): the action handler `entity.import` (parameters `entity`, `columns` = the property of each sheet column in order, `required`, `unique` rules as in `entity.create`, `defaults`, `file`, `skipRows`, `maxRows`, `redirect`) imports an .xlsx into a registered entity: the file passes the upload guard (profile spreadsheet), the entity's create permission and roles are checked by the code, every value goes through the declared length and range, a row is written like `entity.create`, a duplicate (also one repeated in the file) or an invalid row is skipped and counted. A form with a `file` field posts to it; the Excel export is `file.export` over the grid data source; both buttons are instances in the toolbar region of the list page (`button` to the form, `action-button` to the export). The Import Center entry of an import that is a definition carries `Url`.
- **A service that keeps its rules and messages is the write path of a generated page** (batch 5, SCRUM-682): when a master-data service validates and answers with resource-key errors (`DisciplineOpResult`), its methods carry `[PemsOperation]`, the generator spec uses `create_op`, `edit_op` and `row_ops` (the entity layer only loads the edit form), the grid data source is an `operation` provider over the list method (counts included), and the shared resources turn the error key into text in both languages. The old controller's permission is the `permission` of the operation and of the catalog entry; a test asserts both.
- **A statistics object as a record binding** (batch 5, SCRUM-668): a record binding with `"first": true` reads the first row of a /d/ source (a read operation that answers one object has no id), so KPI tiles and a `record-view` can show one object; lists inside the same answer are separate operations. A read that must show tuples or nested lists gets an operations interface in `PEMS.Application` with flat record rows and an implementation over the existing service (the Engineering Copilot page, `IAiInsightsOperations`); the page is several instances in one region (`content-blocks`, `data-grid`, `kpi-tile`, `record-view`).
- **The identity of a read is the context, a row can carry its link** (batch 5, SCRUM-730): a read operation takes `context:employeeId`, `context:roles` and `context:culture` (never an id typed on the page) and answers rows with labels already in the user's language (`IMyWorkOperations`); a row action url may contain `{raw.field}`, a path of this site the row carries (anything else is dropped), so a grid can open the page of each record; the command palette entry of a converted page carries `Url`.
- **A dashboard is several reads of one service** (batch 5, SCRUM-673): the numbers of a service DTO are split into one-row operations (tiles and `record-view` with `first`), count lists (grids of name and count) and a backlog list, in `ICmmsOperationsReads`; the permission of the old controller is the `permission` of the operations and of the pages; labels use the shared resources in the user's language (`context:culture`).
- **A search page takes the page query as the search** (batch 5, SCRUM-703): the url of a grid may carry the page's own query (`/d/key?q={{params.q}}`, so the top-bar search form can open the page with its text), the text becomes the argument `param:search` of the operation, and a filter the operation took as an argument (`param:name`) is not applied to the returned rows again. The operation may use the request (the url helper) through `IHttpContextAccessor`; it still asks the same service as before.
- **A filter bar is a definition** (batch 5, SCRUM-747, 713, 669): the component `page-filters` (fields `select`, `text` or `date`, values `{{params.name}}`) is a GET form, so the filters come back as the query of the page; the grids of the page carry them in their url (`/d/key?f.projectId={{params.projectId}}`), the read operation takes them as `param:projectId` and a filter the operation took is not applied to the rows again. The choices of a select come from a data source with `bindings.filterOptions` (`[{ field, source, valueField, labelField }]`), read by the page host with the rights of the user. A report or search page is a bar plus grids, tiles and record views.
- **Domain logic stays in services**, exposed as `[PemsOperation(Model, Action, Permission?)]` and run by the one handler `operation.invoke` (settings: args sources, `guard`, `sectionGuard`, options objects). A controller that talks to `PEMSDbContext` directly needs its service extracted first (91 of 140 controllers today).
- **Inventory before backlog (learning 2026-11-19).** Before creating issues for a migration, run `python tools/definition-audit/audit.py --write`; the table `plan/sheets/definition-inventory.md` is the checklist, every controller is one issue ("Convert XController to definitions") or marked host/static (SCRUM-628). A backlog written from memory missed 150+ tasks. The remaining gap classes the audit found and the engine issues that close them: file results (SCRUM-615), inline scripts (616), shared layout/partials (617), TempData messages (618), specialised components (619-627), routes (768).
- **No slice left behind.** An issue is converted completely (all actions, views, scripts, roles, rules, feed) or split into separate issues before it starts; "remaining: ..." in a Jira comment is a defect of planning, not a follow-up. Each conversion lists its browser QA lines. **A gap found while working is an issue of the same batch and sprint** (chapter 07 section 1c), never a line of the QA checklist and never a sentence in a comment.
- **Change manifest.** Every change declares migration, feed data, definitions or none (SCRUM-585); definitions ship as migrator feed, not as code. The declaration is in the pull request description (`migration:`, `feed:`, `definitions:`, template line "Change manifest"); a definition file under `PEMS.Persistence/Definitions/System` is the shipped form of a definition, a schema change is a migration, rows the customer receives are feed. The retrofit table of the Sprint 2 work is `plan/sheets/change-manifest-audit.md`.
- **The definition workbench is itself definitions** (SCRUM-449, 450, 451, 455, 419, 609): the list, details, kinds, storage and missing-translations screens are stored pages (`definition-workbench`, `definition-details`, `definition-kinds`, `definition-storage`, `definition-translations`) over the data sources `definitions-grid`, `definition-kinds-grid`, `definition-usages-grid`, `definition-largest-grid`, `definition-translations-grid` (providers in `DefinitionWorkbenchProviders`, permission `Definitions.View`). Create, save a draft, validate, publish, roll back and discard are the operations `Definition.*` of `IDefinitionWorkbench` run by `operation.invoke` from stored forms and actions (`definition-create`, `definition-save-draft`, `definition-validate`, `definition-publish`, `definition-discard`, `definition-rollback`); the files are generated by `tools/definitions/make_workbench.py`. Designers (form, page, action, data source, menu) are the same kind of thing: a stored form or page over a draft, never a compiled screen.
- **Impact before publish or rollback** (SCRUM-450, 457, 459): `IDefinitionImpact` answers read-only. `UsedByAsync(kind, key)` lists the published definitions that point at one; `PrecheckPublishAsync` and `PrecheckRollbackAsync` return `allowed`, `warnings` or `blocked` with items (path, message): a reference to a definition that does not exist or is not published is blocked, a form field that disappears is blocked (stored values would be lost), a changed field type, a field that became required and a removed property are warnings (`DefinitionCompatibility.Analyze`, generic per kind). The workbench publish and rollback stop on `blocked` with the report text. The REST publish and rollback are not changed by this (the OpenAPI snapshot stays); enforcing the same check there is a later issue.
- **The migration package** (SCRUM-581, 583): one zip, signed by the vendor, installs, updates or feeds a customer. `manifest.json` (format 1: kind install|update|feed, from and to version, schema level, definitions, data sets with mode append|overwrite|merge, SHA-256 of every other file, signer key id, ECDSA P-256 signature over the manifest without its `signature`, compact) plus `definitions/*`, `data/*`. `MigrationPackage.Read` refuses a non-zip, an unknown format or kind, an untrusted signer (public keys are configuration `Migrator:TrustedKeys`, never in the repository; the private key stays in the vendor tool, SCRUM-584), a changed manifest, a changed, missing or unlisted file. `MigrationPackage.Detect` compares it with the database: install needs an empty database, update needs its from version and a newer target, feed needs an installed database and is a refeed when the package hash was fed before. `FeedPlanner` is the dry run of a feed over the entity catalog rows (append, overwrite, merge; refused: no key, key twice, failed validation; a rerun changes nothing); applying a plan goes through the entity write actions, never per-entity feed code. The migrator center (SCRUM-582) is the form `/f/migrator-inspect` (SystemAdmin): upload a package (upload profile `migrationPackage`, a zip up to 100 MB), operation `Migrator.Inspect` verifies it against `Migrator:TrustedKeys` and says what the migrator would do; nothing is changed (the run is SCRUM-814). The vendor builds packages with the panel forms `/f/packager-feed`, `/f/packager-install` and `/f/packager-update` (operations `Packager.*`, SystemAdmin): signing needs `Migrator:SigningKey` (a PKCS#8 private key, base64) and `Migrator:SignerKeyId`, set in the secrets env file of the **vendor's own deployment only** (owner decision 2026-11-20: never in the repository, never on a customer installation); without them every operation refuses, and a built package is verified against its own public key before it is downloaded.
- **Safe publish** (SCRUM-785, 788, 789): the REST publish checks the references first (`422` with the pointer when a target is missing or unpublished), needs `?acknowledge=true` for a change that only warns (`409 breaking-changes-not-acknowledged`), runs a smoke check after the publish (the published version against today's definitions, inside `Definitions:SmokeTimeoutMs`) and, when it fails, publishes the previous version again (`409 auto-rolled-back`, change summary `auto-rollback: reason`); the automatic rollback never loops: when the previous version is not safe either it stops, logs an `ALERT` and answers `409 smoke-check-failed`. Read-only endpoints: `GET /definitions/{id}/used-by`, `/references`, `POST /actions/precheck-publish`, `/actions/precheck-rollback`. Code: `DefinitionPublishGuard`. Storage report: growth per month, cache counters and the size warning (`Definitions:StorageWarnMb`) on the page `definition-storage`; retention is `Definitions:RetainRetiredVersions=forever` only (any other value stops the start).
- **Who may change a definition** (SCRUM-440, policy table, enforced by the permission matrix; module `Definitions`): view (`Definitions.View`) opens the workbench, the designers and the reports; create (`Definitions.Create`) makes a definition and an action; edit (`Definitions.Edit`) edits a draft (the designers, save draft, validate, discard); approve (`Definitions.Approve`) publishes and rolls back, in the REST API and in the workbench alike. Targets: a platform field of a shipped form is changed only by a product update (`FormOwnership`, platform-field-changed, -removed, -added); an application field, a page, a menu, an action and a data source are the customer's and are changed by whoever holds Edit and published by whoever holds Approve; a whole shipped definition can be reset to its shipped version by Approve (`reset-to-shipped`); every change is audited by the context's SaveChanges with who, what and when, and the version history keeps the payload. **Two-person publish** (SCRUM-808): the setting `Definitions:ProtectedDefinitions` (`kind:key` or `kind:*`, comma separated, empty by default) names the definitions that a person other than the author of the draft must publish (REST publish `409 second-approver-required`, the workbench refuses with the same text); the permission `Definitions.Approve` is still needed. `DefinitionPolicyTableTests` has one test per cell of this table (each REST endpoint and each workbench operation) and fails for an endpoint or operation that is not in it. The decision is a second person with the permission, not a workflow instance (the workflow platform can take over later).
