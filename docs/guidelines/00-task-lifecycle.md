Use the Atlassian MCP tools (or the Jira UI for humans) for every step. Never skip a status change.
Field ownership between the plan files and Jira: [PLAN_TRACKER_WORKFLOW.md](../process/PLAN_TRACKER_WORKFLOW.md).

## 0. Start of every work block (owner decision 2026-11-04)

A **work block** is everything done between one go-ahead and the hand-over of its issues to In Review. **Any go-ahead opens one**: "continue", "next", "yes", "do it", "go on", a named task or a list of tasks, a session that starts with a task. A question or a request to look something up is not a go-ahead. Run the four steps below **before the first edit of the block**, and say in your first message that you did (a line per step is enough). If the same session keeps going after a finished block and the owner says "continue" again, that is a new block: repeat the steps, they are cheap when nothing changed.

### 0.0 The words we use for grouping work (owner decision 2026-11-06)

One word, one meaning, from the biggest unit to the smallest. Use these words, and only these, in Jira comments, plan rows, pull requests, commit messages and chat; if a message needs a new grouping, add it here first.

| Word | Means | Where it lives | Example |
|---|---|---|---|
| **milestone** | a product stage with a goal, M0 to M6 | an Epic in Jira (SCRUM-5 to SCRUM-12), `milestone-mN` label | M1 Dynamic core, components and licensing |
| **sprint** | a time box of the Jira board; holds the issues started in it | Jira sprint field (`customfield_10020`) | Sprint 1 (id 5) |
| **issue** | one unit of tracked work: one Jira key, one plan row, one definition of done | Jira + `plan/rows/NNNN.md` | SCRUM-339 |
| **work block** | everything done between one go-ahead and the hand-over of its issues to In Review (section 0) | the session | "the page-level block" |
| **batch** | issues (or the slices of issues) that share an area, files, a pattern or a dependency chain, done together on one branch | the first message of the work block | "icons + styles" |
| **slice** | one safe, independently mergeable piece of one issue: its own branch or commit set, its own pull request, merged at once. An issue with more than one slice names them `slice 1`, `slice 2` ... in its Jira comment (not `P1`, `phase`, `part`) | a pull request | SCRUM-339 slice 1 = page wrappers, slice 2 = flex |
| **wave** | a set of **pages** migrated together to the page templates; only for the page migration issues (SCRUM-342 to 346: W1 to W5). Never a name for a group of tasks or components | one issue per wave | W1 pilot: Admin area |
| **family** | a group of related components or tag helpers converted or documented together | a UI component chapter | the list family (`pems-list-*`) |
| **part** | a child tag of a component that has no meaning outside it (`FacadeKind.Part`, e.g. `pems-list-chip` in `pems-list-chips`). Not a piece of an issue (that is a slice) | the registry | `pems-related-add` |
| **pattern** | one kind of hand-written markup the adoption ratchet counts and a component replaces | `AdoptionRatchetTests` | `flex`, `icon`, `content-card` |
| **step** | one ordered action inside a procedure, a checklist or a slice | guidelines, plans | "step 3 of section 2" |
| **phase** | a stage inside a design document or specification (an ADR, an RBAC spec). Not used to group tasks | ADRs, specs | "RBAC phase 3" |
| **tier** | how often a test group runs: tier 1 every task, tier 2 every cross-cutting batch, tier 3 end of sprint (guideline 07) | guideline 07 | the Web family is tier 2 |
| **follow-up** | work found while doing an issue that is not part of it: a named unchecked QA line or its own issue, never silently dropped | Jira, QA checklist | "add el()-builder counters" |

How they nest: a **milestone** holds **issues**; a **sprint** holds the issues started in it; a **work block** takes **batches** of issues; an issue is delivered in one or more **slices**, each its own pull request. A **wave**, a **family** and a **pattern** are not levels of this nesting: they describe *what* is migrated (pages, components, markup kinds).

### 0.1 Pull `main`
`git fetch origin`, then update `main` (an app worktree uses `sync_with_base_branch`; a checkout with local changes you did not make is left alone, you only report it). Look at what merged since your last block (`git log --oneline <last-seen>..origin/main`): other sessions change the pages and tests you are about to touch. Branch from the fresh `main`. Never plan from a stale checkout.

### 0.2 Audit the whole backlog, not only the task you were pointed at
Read every open issue of the project, not one area label: `project = SCRUM AND statusCategory != Done ORDER BY key` (Epics skipped), plus your own In Progress issues. Compare each with the **current code** and with its neighbours, with the method of section 1 step 2a (ratchet baseline, greps, registry, merged PRs, plan row; never the description alone). Give every issue one verdict, written in one line:

| Verdict | Meaning | What you do |
|---|---|---|
| go | the description still holds | keep it in a batch |
| modify | counts, pages or scope changed | edit the issue text and the plan row, or post the new scope as a comment, then keep it |
| split | a part is blocked, needs a decision, or is another kind of work | a part with a different owner or blocker becomes its own issue (section 5d) or a clearly named unchecked line; the rest goes on |
| merge | it overlaps a neighbour (rule 28) | do it inside the neighbour's batch and say so on both issues |
| cancel | already done, superseded or no longer wanted | comment the reason and the evidence; move to **Cancelled** only with the owner's yes |
| blocked | a dependency is not Done and is not in your block | name the blocker; if the blocker is itself a To Do issue, pull it into the block instead of waiting (step 0.3) |

**Partial work** (owner decision 2026-11-19, checked the same day): the issue's Jira status wins. A Jira issue that is still open (To Do, On Hold or In Progress) with part of its work already on `main` is moved to In Progress and finished, in the batch that fits it; it never waits in To Do or Hold while its remaining part is known. A plan row with the status *Partial* whose Jira issue is Done or In Review is **not reopened**: the row records a remainder (checked on 2026-11-19: all 54 Partial rows were of that kind, none was open work); the remainder is placed in the batch that covers it or raised as its own issue (`plan/sheets/sprint-batches.md`, section on Partial rows). What cannot be finished (needs an owner decision, SQL Server, a browser) is split into a named unchecked QA line or its own issue, and the rest of the issue goes on to In Review.

A thorough audit of hundreds of issues is not required at full depth every time: read all titles and labels, read in full the ones that touch the area of the go-ahead or share a dependency chain with it, and say which you only skimmed. Never skip the step.

### 0.3 Group the survivors into related batches and do each batch together
- A batch is issues that share an area, files, a pattern or a dependency chain. **A blocker travels with the issue it blocks** and is done first (a To Do blocker is not a reason to stop: it is part of the batch, unless it needs the owner's decision or an unavailable tool).
- One branch per batch, named after the primary issue; each safe slice is its own PR and is **merged at once** (section 4); every issue of the batch is started in Jira in one step (assignee, active sprint, In Progress, plan comment: section 1 step 5) **before** its first commit, never after.
- **No finished issue waits on the branch** (owner decision 2026-11-19). In a batch, an issue whose *Done when* is met and whose tests ran green is merged and moved to In Review (`qa-pending`, QA checklist with the unrun checks) as soon as its tests pass, in reasonable groups of issues that belong together (a dependency chain, one area), not one pull request per tiny piece and not everything at the end of the batch. Work that is not finished stays In Progress with a draft checklist and says why; it is never merged as if it were done. A finished issue left unmerged while the batch goes on is a defect: the branch drifts, other sessions work on stale code, and the hand-over to QA is delayed.
- **Claim the whole batch first (owner decision 2026-11-19).** The moment the batch is approved, before any code, move **every** issue of it to In Progress in one step (assignee set, in the sprint, a one-line comment naming the branch): other agents and people pick untouched To Do issues, and an issue that is only planned looks free. An issue the batch does not reach goes back to To Do with a comment saying why; an issue is never left In Progress without a branch or a person working on it. Check with `status = "In Progress" AND key in (...)` that the count equals the batch.
- **Hand over lean**: each issue of a batch leaves for In Review with the minimum tests that are really needed; every other check is an unchecked QA line, and the nearly repeated tests of the batch are merged at its end (guideline 05 test budget, 07 section 2a).
- **Batches are big: 10 to 30 related issues** (owner decision 2026-11-19), ordered by dependency (`plan/sheets/sprint-batches.md`); the engines first, then the conversions that only add definitions. One branch, one PR per safe slice, one Jira comment with a QA checklist per issue.
- **Hand over with the minimum tests that are really needed** (owner decision 2026-11-19): before an issue goes to In Review the author runs only the tests that can catch a regression of what was changed and that cost seconds (the new tests of the issue and the exact classes that mention the changed files); every other check, however useful, is **not run** and goes onto the QA checklist as an unchecked line (`not done - <why>`) with the exact command, so the tester or the end-of-batch and end-of-sprint runs do it. A test added for an issue covers its Done-when and its risky edge, not every combination.
- **Build once, at the end of the batch** (owner decision 2026-11-19): a full build of the solution costs 10 to 20 minutes on a busy machine, so a batch builds once, when its last issue is written, together with the heavy tests (tier 2). A slice is written carefully, read through once for compile errors (usings, signatures, every call site of a changed method, the tests that construct a changed type), and merged without a build; when the change lives in a small project (for example `PEMS.Application`) a `dotnet build` of that project alone (about a minute) is the allowed compile check. The build at the end of the batch is mandatory: a break it finds is fixed at once in a commit named `SCRUM-<key>: fix build of the batch (hamid)`, before any further work, because other sessions pull `main`. The issues list the tests that could not run for lack of a build as `not done - end-of-batch build and run` QA lines.
- **Light first, huge last** (owner decision 2026-11-19): inside a batch the issues are ordered by weight as well as by dependency. The small and medium issues come first and each slice is checked with **light tests** (the exact classes of what changed and the guard classes, about a minute: `gates.py --slice --run`), then merged and moved to In Review at once. The **huge issues** (effort L, a schema change, a new engine with a UI, anything that needs the whole definition or API suite) are done at the end of the batch, and the **heavy tests** (whole test namespaces, the API conformance and baseline suites, the UI test project, the full definition suite: plain `gates.py --run`) run **once, at the end of the batch**, not after every slice. A dependency still wins: a huge issue that a light one needs goes first, and is then checked with the light tests of its own classes. Three levels of testing, named by the existing tiers (chapter 00 section 0.0): **tier 1, light** after each slice (the exact classes and guard classes, `gates.py --slice --run`); **tier 2, heavy** once at the end of the batch (whole definition and validation namespaces without SQL, the API suite, the UI tests: `gates.py --run`); **tier 3, very large** only at the end of the sprint (owner decision 2026-11-19): the whole `PEMS.Tests.Web` namespace, `dotnet test PEMS.slnx` and the SQL Server families. A batch never runs tier 3; the issues list it as `not done - end-of-sprint QA` lines with the exact command (chapter 07 section 2b).
- Do not take one issue at a time when its neighbours share the work; do not widen a batch past what one person could review (a batch is related work, not "everything open").
- Work that needs the owner's decision, SQL Server, a browser or a production host is split off and listed (unchecked QA lines or a named follow-up); it never holds a batch back.

### 0.4 State the plan, then work
The first message of the block lists: the batches and their issues in order, what the audit modified, merged, split or proposed to cancel (with the evidence in one phrase), and what is blocked and by what. **The go-ahead that opened the block is the approval of this plan** (it satisfies the "ask and wait" of step 5); anything outside the plan needs a new yes, and every cancellation needs the owner's yes. Then work through the batches without asking again.

### 0.5 Close the block
**Merge nearly repeated tests at the end of the batch** (owner decision 2026-11-19): when the last issue of a batch is done, read the test classes the batch added or touched and merge tests that repeat each other (the same arrangement with another value becomes one `Theory`, the same fixture in two classes becomes one helper, a test that another test already proves is deleted), without losing a case. Run the merged classes once; the diff of this step is its own commit of the batch (`SCRUM-<key>: merge repeated tests (hamid)`).

**No finished issue waits on the branch** (owner decision 2026-11-19). In a batch, an issue whose *Done when* is met and whose tests ran green is merged and moved to In Review (`qa-pending`, QA checklist with the unrun checks) as soon as its tests pass, in reasonable groups of issues that belong together (a dependency chain, one area), not one pull request per tiny piece and not everything at the end of the batch. Work that is not finished stays In Progress with a draft checklist and says why; it is never merged as if it were done. A finished issue left unmerged while the batch goes on is a defect: the branch drifts, other sessions work on stale code, and the hand-over to QA is delayed. At the close of the block every issue is therefore either In Review or still In Progress for a stated reason.

**Heavy tests wait for the end of the batch or of the sprint** (owner decision 2026-11-19): during the block only the light tests run per issue (build and the exact classes touched, no broad namespaces); the heavy families run once at the end, and only after the owner has been asked when the whole batch is In Review ([chapter 5, Test budget](05-environment-and-commands.md)).

**When the work of an issue is finished, the agent goes straight on, without asking** (owner decision 2026-11-20): open the PR, and merge it when the owner has said "merge" for that batch or said to go ahead non-stop; right after the merge the issue gets the label `qa-pending`, the QA checklist (chapter 07 section 1c) and the status In Review, in the same step. An issue never waits In Progress for a question the owner already answered; if the merge is not allowed yet, the agent says so once, names the PR, and continues with the next claimed issue.

**No build and no test run without the owner's input, and no new batch unless the owner says so** (owner decision 2026-11-19): an agent never starts a `dotnet build`, `dotnet test`, `gates.py --run` or a browser run on its own, not even "just the changed project"; it asks first, naming what it would run and why. A go-ahead on a batch is not an answer to this. When the owner stops a batch, every issue the agent claimed and did not finish goes back to To Do (status only; the work already merged stays), and the agent reports the finished batch and waits.

Every issue of the block ends in In Review (conditional done, `qa-pending`, QA checklist with the unrun checks) or with a one-line reason why not (blocked, needs a decision, only part done and still In Progress). The last message says, per issue: merged PRs, tests run and not run, and what is next. Update the guideline if the block taught something durable (chapter 6).

### Anti-patterns (each one happened)
- Starting the issue the owner named without looking at its blockers or neighbours (SCRUM-467 was found blocked by SCRUM-464 and 363 only after reading it).
- Merging work under an issue that was never moved to In Progress (SCRUM-347).
- Planning from a stale checkout, or from an issue description that is weeks old (SCRUM-337 said "342 hand-written tables" when all of them were already components).
- Stopping at a blocker that is a To Do issue of the same area instead of doing it first.
- Treating "continue" as a reason to skip the audit because the last block did one.
- Starting a batch's code while its issues were still To Do, so another agent could take one (2026-11-19: claim the batch first).
- Leaving an issue of a started batch in To Do (owner decision 2026-11-19): while a batch is started, **every issue of it that is To Do, existing or created later for it (an engine input, a gap), goes to In Progress at once**, assigned, in the sprint; In Review only after the merge. An issue that is not part of the started batch stays To Do. **Check it twice**: when the batch starts, and every time you create an issue for the started batch (search `sprint = <id> AND status = "To Do"` before you write code); a started batch with a To Do issue is a collision risk. The same rule is in `plan/sheets/sprint-batches.md`. **The batch table there has a Status column (Not started, Started, In Review, Tested, Closed): update it in the PR that starts the batch, when its last issue goes to In Review, and when its tests run** (owner decision 2026-11-20).

## 1. Before you start (the "Step 0" checklist)

1. **Read this guideline** (README reading map). Skim the last entries of the [learnings log](learnings-log.md).
2. **Read the issue** (`getJiraIssue`): *Why*, *What to do*, *Done when*, *Depends on*, Plan ID, parent, sprint, comments.
   Also read the matching backlog row `plan/rows/NNNN.md` (`python tools/plan-sync/plan_sync.py show <id>`: Evidence, Prompt, Requirement, Depends) - Jira shows a copy, the plan owns scope.
2a. **Re-audit the scope against today's code before you start** (owner decision 2026-11-04). A task is written at one date and started at another: pages were converted, components added, other tasks merged in between. Before the first edit, measure the task's "What to do" against the current repository (counts from the ratchet `tools/UiAudit/adoption-baseline.json`, a grep of the views, the registry, open and merged PRs of the area) and decide, in the plan comment, one of:
   - **go as written** (the numbers still hold);
   - **modify** the scope (update the issue text and the plan row: new counts, the pages that really remain, the pages that turned out not to be of this kind, such as a dashboard in a list task);
   - **split** it (a part needs an owner decision or another task's result: make it its own issue with a parent and labels) or **merge** it into a neighbour (rule 28, no duplicates);
   - **cancel** it because the work is already done or no longer needed (see the cancel rule below).
   Always work from the **current state** of each page, never from the old description of it, and never convert a page back to older markup. Then start.
   **Cancelling an issue** (owner added the **Cancelled** status to the SCRUM workflow, 2026-11-04): a task that is already done elsewhere, no longer needed, or replaced is moved to **Cancelled** (`transitionJiraIssue` with `transitionName: "Cancelled"`) with a comment that states the reason and the evidence (PR, test, ADR, the issue that replaces it). Cancelled is not Done: it needs no QA and counts as no delivery. Ask the user first, never delete an issue and never leave a dead one open.
3. **Check dependencies.** If any blocker is not Done, stop and tell the user before writing code.
4. **Study related Jira issues.** Search the project (JQL on Plan ID, area label `area-<name>`, summary keywords, same epic/milestone):
   open, in-progress and recently Done issues that touch the same area. Read their comments and commits. Goal: no duplicated work,
   no contradicting design, and reuse of what a neighbour task already decided.
5. **Look for similar tasks to batch.** If two or more open issues are close (same component, same files, same migration, same
   library, same research), propose doing them together. **Ask the user and wait for approval before starting a batch** (a go-ahead that opens a work block, section 0, is that approval for the plan you state in your first message). State: which
   issues, why they belong together, what changes in scope, and what each issue's "Done when" will be checked against.
   Never silently widen the scope of one issue to swallow another.
   **When a batch starts** (owner decision 2026-10-29; approval alone changes nothing in Jira): in one step every issue of the batch is moved into the **current (active) sprint**
   (`transitionJiraIssue` with the active sprint id from `listJiraBoardSprints`, state `active`), moved to **In Progress** and **assigned** to the person doing the work (the Jira user of the
   developer running the session; account id from `atlassianUserInfo`, `editJiraIssue`). Planned, approved or newly created issues stay **unassigned and outside any sprint**: a To Do issue
   is never in a sprint and never has an assignee (the exception is `qa-failed`, section 5a). Do this before step 2 of section 2.
   **Moving an issue to In Progress does NOT put it in the sprint** (found 2026-11-01: eight issues of a long component batch sat In Progress / In Review in the backlog because only the status and the assignee were set).
   The sprint is its own field: `editJiraIssue` with `fields: {"customfield_10020": <sprint id>}` (the active sprint id is on any issue already in it: read `customfield_10020.value[0].id` of a sprint issue, or use `listJiraBoardSprints`; Sprint 1 is id 5 while it is active).
   Do it in the same step as the transition, for **every** issue you start, including an issue you come back to (it goes back to In Progress) and a sub-issue you create for the batch. Then **verify**: `key = SCRUM-N AND sprint in openSprints()` must return the issue; do not report the issue as started before it does.
5a. **Ownership check - no collisions.** Before starting any issue (alone or in a batch) look at its assignee and status:
   - assignee is another person, **or** the issue is already In Progress / In Review, **or** a branch/PR for it exists -> **do not touch it**. Ask that person (through the user, or a Jira comment mentioning them)
     and get an explicit yes before starting. Keep the confirmation in a comment (who agreed, when). Until then work on something else.
   - the same applies to files and areas that another person's in-progress issue changes: if your task overlaps with it (same files, same migration, same component), stop and coordinate first.
   - an unassigned To Do issue may be taken; assign it to yourself in the same step.
   - a To Do issue labelled `qa-failed` keeps its previous assignee: if that is you or the user told you to take it, move it to In Progress and start from the defect comment; otherwise ask the assignee first.
   Never reassign, move, close or edit an issue that belongs to someone else without their confirmation.
5b. **Adding or changing a task - study first** (Instructions rule 28, owner decision 2026-10-26). Before you add a backlog row and Jira issue, search the backlog and Jira by area, files, goal and keywords (Done and Open rows; held tasks count as not open). If an existing task covers the work or can absorb it, **modify that task**: extend What to do and Done when in the plan row file and the Jira description, and comment what changed and why. Add a new row only when none fits. **A new row's Plan ID is the number of its Jira key** (owner decision 2026-10-27: SCRUM-423 gets `#423`, so the two numbers read the same): create the Jira issue first, then write the row with `#` = that number; gaps in the `#` column are fine. Rows created before this date keep their old numbers (SCRUM-418 is `#388`) - never renumber them. Give it and name the tasks you checked in its Evidence.
5c. **Your task overlaps a started task of someone else** (owner decision 2026-10-27, SCRUM-413 / SCRUM-280). Do not edit it. Build the near-term slice as its own task, say in the issue what the slice covers and what stays with the other task, and ask the owner of the other task (comment mentioning them, or through the user) to confirm the link; reuse the same files and workflow so there is one pipeline, not two. When the other task merges, re-read its comments and diff and **narrow your not-started rows** to what it does not cover (plan row file, Jira description, a comment saying why); do not leave a plan that repeats finished work.
5d. **Creating a Jira issue - the checklist** (owner decision 2026-10-31, SCRUM-479; the 2026-10-31 audit found issues without an epic, without a `[#N]` title, without labels and a missing plan row, all created by hand from memory of the rules). Every issue, whoever creates it (a session, the shared `pems ata` account, a person), is created with **all** of these in the same `createJiraIssue` call, and only then does the plan row follow:
   1. rule 28 done: backlog and Jira searched; the tasks checked are named in the description;
   2. `parent` = the milestone Epic of the plan row (SCRUM-5 M0, -6 M1, -7 M2, -8 M3, -9 M4, -10 M5, -11 M6, -12 existing capabilities); no epic, no issue;
   3. labels `area-<name>`, `doer-claude|doer-user`, `effort-<XS|S|M|L|XL>`, and (as soon as the key is known) `plan-<key number>`; add `milestone-mN` if the row has one;
   4. the key number is only known after creation, so **in the same step** edit the summary to `[#<key number>] title` and add `plan-<key number>`; a title without the prefix is not finished;
   5. the description has Why / What to do / Done when / Depends on (a bug: reproduction steps), a bug is an issue of type **Bug** (section 3a);
   6. assignee: you, or unassigned for a split-off follow-up; then `plan_sync.py new <key number> "title" area=... group=... milestone=...` and `check`, in the same pull request or the next one;
   7. a duplicate is never created: modify the existing task (rule 28); a created duplicate is labelled `duplicate` and closed by the owner.
   `python tools/plan-sync/plan_sync.py tracker-check` enforces points 2, 3, 4 and `qa-pending` on In Review for every issue from SCRUM-400 on (nightly job and pull-request check once the `JIRA_*` secrets of SCRUM-475 exist). When you touch an issue that fails the checklist, correct it in the same step and say so in the comment.
   **No Jira field enforces this** (owner decision 2026-11-09, SCRUM-557): the project is team-managed, its create screen does not require *Parent* and has no *Plan ID* field. The Plan ID is the `plan-<n>` label together with the `[#n]` title prefix, and `tracker-check` is what enforces Parent, labels and title.
   **Until SCRUM-475 is done the agent is the check** (the nightly job cannot run without the `JIRA_*` secrets). So:
   - **Read back** every issue you create, right after creating it (`getJiraIssue`, fields `summary`, `parent`, `labels`, `status`), and confirm points 2, 3 and 4 above; correct what is missing before you do anything else.
   - **Sweep** at the start of every session that creates, transitions or reviews issues, and before you move any issue to In Review: search with the Jira tool `project = SCRUM AND issuetype != Epic AND key >= SCRUM-400 AND statusCategory != Done` (fields `summary`, `parent`, `labels`, `status`) and check each hit against the same rules: parent epic set, `[#N]` title equal to the key number and to the `plan-N` label, `area-*`, `doer-*`, `effort-*` labels, and `qa-pending`, `qa-passed` or `qa-failed` on In Review. Also run `project = SCRUM AND issuetype != Epic AND parent is EMPTY`, which must return nothing.
   - **Sprint sweep** (same moments): `assignee = currentUser() AND statusCategory = "In Progress" AND sprint is EMPTY` must return nothing; put every hit into the active sprint (section 1, "When a batch starts") and mention it in your report. An issue that is In Progress or In Review and not in a sprint does not show on the board.
   - **Fix** metadata findings yourself in the same step (epic, title, labels; never a status or an assignee that is not yours) and say so in a comment; list findings you could not fix, and anything that looks like a duplicate, in your report so the owner sees them.
   - If an export is at hand, `python tools/plan-sync/plan_sync.py tracker-check --json issues.json` does the whole sweep at once.
5e. **The standard way, for every task you create or start** (owner decision 2026-11-05, SCRUM-506). Three steps, in this order, before the first line of code or the first new issue; the result is written in the Jira plan comment (or the description of a new issue), not kept in your head:
   1. **Search Jira and the plan for the same or a neighbouring task**: a JQL search by area, goal, file and keywords (`project = SCRUM AND text ~ "..." ORDER BY updated DESC`, Done and open) and `python tools/plan-sync/plan_sync.py` search of the rows. Name the issues you checked. If one covers the work or can absorb it, **modify that issue** (description, plan row, comment saying what changed and why) instead of creating a new one; split or merge neighbours (rule 28, 5b). A new issue exists only when none fits.
   2. **Research best practice on the internet** (web search, official docs, the library's own repository; the name of a thing too: use the established term, not an invented one). Record 2 to 5 sources with one line each on what you took or rejected from them, and the licence of any library ([chapter 03](03-libraries-tools-and-research.md) section 3). "No source found" is a valid result and is written down too.

## 3a. A reported bug is a Bug issue that goes through the normal flow (owner decisions 2026-10-27 and 2026-11-07)

A bug that a person reports (in chat, in Jira, in a pull request, in another session, or found by a tester or by you outside the task you are finishing) goes through the **same flow as any task**: no silent fixes and no fix that is only a comment on another issue.

1. **Create the Jira issue first, with the issue type `Bug`** (owner decision 2026-11-07: the project has the work type Bug; every defect is a Bug, never a Task or a Story with "Bug:" in the title, and no `bug` label is needed. The earlier rule of 2026-10-27, "a Task in the status `Bugs`", is replaced). The title is `[#n] <what is wrong>`. Its flow is To Do -> In Progress -> In Review -> Done (the status `Bugs` still exists in the workflow but is not needed). A task that was created as a Task and turns out to be a defect is changed to type Bug in the same step (Jira: Edit the work type). Create it with a plan row file in `plan/rows` (`plan_sync.py new <id> "title" track="Bug Fix"`; Track `Bug Fix`, `#` = the Jira key's number, a Plan ID label; the plan row keeps its own Status until the issue moves, Jira owns the real status) and the usual description: *Why* with the reproduction (steps, expected and actual result, culture/browser/role), *What to do*, *Done when* (the reproduction no longer fails), *Evidence* (a failing test, log or screenshot), priority and parent epic. Link the issue that exposed it.
2. **Every known Bug is done in the active sprint** (owner decision 2026-11-08): a Bug is never left in the backlog or parked for a later sprint. When it is created (or an existing issue is changed to type Bug) it is put into the **active sprint** at once (set the sprint field explicitly and verify with `sprint in openSprints()`), assigned, and fixed in that sprint; if the sprint cannot hold it, the owner is told in the same message and decides what leaves, the bug does not. A Bug found in a closing sprint's review stays in that sprint (chapter 07 section 7a step 6). Ownership and planning as for any task (section 1, 5a): assignee, In Progress, "Started by" comment with the plan.
3. **Reproduce with a test first**: a regression test that fails before the fix and passes after it; the bug is not fixed without one (a manual-only bug gets a manual check in the README table instead). If the test cannot run in your session, say so as an unchecked QA line (chapter 07 section 1b).
4. **One branch and one PR** (`fix/SCRUM-n-short-name-<user>`), merge into `main`, then **In Review + `qa-pending` + the QA checklist** with a regression line for the bug and two neighbouring checks; **Done only after QA** ([chapter 07](07-qa-check-in-the-ui.md)).
5. **Exception, only this one:** a bug you find in your own task *before* it is merged is fixed in that task's pull request and named in its comment. After the merge it is a Bug issue like any other. A defect found during a QA check follows chapter 07 section 4 (back to To Do) and is also linked as a Bug issue when it is more than a one-line fix.

## 3b. Preventing bugs: the defect classes of the Sprint 1 review (owner request 2026-11-10)

The Sprint 1 review (SCRUM-524, 525) found 26 Bugs (SCRUM-526 to 560) in work that had been marked In Review. Almost all of them belong to eight classes. Before you move an issue to In Review, check the classes your change can touch; each rule has a test or a QA line, not only a sentence.

1. **A merge or conflict resolution drops lines from a shared file** (526, 527, 536: a stylesheet, `pems-actions.js` and the script templates fell out of `_Layout.cshtml`; the templates came after the scripts that need them). After resolving a conflict in `Views/Shared/*`, a layout, `site.css` or `pems-ui.css`, read the diff of your branch before the merge against the result for that file and keep both sides' lines. A layout test pins that every layout (`_Layout`, `_AuthLayout`, `_LayoutEmbed`) loads its stylesheets and scripts and renders each template set **before** the first script that uses it.
2. **A component conversion changes behaviour that the golden file does not show** (528 link buttons without `href`, 551 a stat grid that only exists in admin CSS, 541 the sidebar marker drawn twice, 533 tests that pinned attribute order, 560 and 537 scripts that look for a removed element or mark their own container). Test the converted element through the real tag-helper pipeline with the attributes the views use (`asp-action`, `asp-route-*`, `data-*`, `disabled`, a nested tag helper), not only with the options record. A style a component needs belongs to the component (`pems-ui.css`), never to a page or admin stylesheet. When you remove or rename an element or a `data-` attribute, search the scripts (`wwwroot/js`) for its selector in the same change. Assert on the element and its attributes, never on attribute order or neighbouring text.
3. **A feature that was never finished** (544 a POST action with no form, 545 an edit form missing fields the service overwrites with null, 530). For every controller POST action there is a view control that reaches it; for every edit form a test saves one field and checks that all other fields are unchanged; a test finds the actions that no view posts to (search of `asp-action`).
4. **A flow that works for SystemAdmin but not for the default roles** (546, 547: a role without the permission is offered as approver, a Hold task lands with someone who cannot open it, a Buyer cannot open the page for the decision). Every workflow step is tested once with the default grants of `RoleCatalog` for the role it is routed to, and a role list in a screen offers only roles that hold the needed permission.
5. **Missing validation and messages** (539 an empty project is saved, 558 duplicate project codes, a refused save with no message, 540). Required and unique rules are on the model and checked on the server; every create and edit form has the validation summary; a refusal always tells the user why.
6. **English text, Gregorian pickers and wrong links on Persian pages** (540, 552, 543, 548). User-visible text goes through the localizer (including `ViewData["Title"]`, Identity errors and model messages); no `type="datetime-local"`; links are built with `Url.Action` or a route helper, and a test resolves every URL a provider (search, menu, notification) can produce to an existing action.
7. **A statement in a document or a workflow that is not true** (556 the runbook claims branch protection that does not exist, 557 a required field that is not required, 555 a workflow step that cannot show an error). When you write that something is enforced, run the command that proves it and put the command in the document.
8. **The test or the machine, not the product** (534 CRLF checkout, 532 `.dockerignore` without local tool folders, 535 a load script that loses its cookies, 533 a test host that did not register PEMS.UI, load-dependent timing tests). A new file type or folder gets its `.gitattributes` and `.dockerignore` decision in the same change; a test host that renders views registers `AddPemsUi`; a test with a time budget is run alone before it is called red.

9. **A component conversion that stops at the pattern the author searched for** (SCRUM-521 first pass, 2026-11-14: only the tab *buttons* were converted; the server-side tab strips, the notification filter pills, a jump link to a tab and the 104 sidebar links were left as "different things" and the owner found them). A component task converts **every** hand-written form of the thing, not the one form the first search found. Before In Review: (a) search the old markup by its class and its attributes in all spellings (`grep` for `nav-link`, `nav-tabs`, `data-bs-toggle`, the tag, in `.cshtml`, `.razor` and `wwwroot/js`), list every hit and classify it; (b) a hit that is the same thing in another spelling (anchor instead of button, `li` or no `li`, a sidebar entry) is converted in the same change, by giving the component an option, not left behind; (c) a hit that really is something else gets its own named component or its own issue **before** In Review, never "by design" in a comment only; (d) the adoption ratchet counter matches the whole old pattern (every element that carries the class), so the baseline is `{}` only when nothing is left; (e) the PR text lists the searches that were run and the count left, and says 0 or links the issue for each remainder.

Two process rules came with them: (a) **every Bug and every issue gets its plan row when it is created** (539 to 557 had none until the review ended); (b) **a Bug is not In Review without the regression test that failed before the fix** (section 3a step 3). The checks of this section are lines of the issue's QA checklist when they cannot be a test.

## 4. Finishing the issue - two levels of "done"

| Level | Jira status | Meaning | Who/when |
|---|---|---|---|
| **Conditional done** | **In Review** | Work is complete and verified by the author: every *Done when* item met, **the PR is merged into `main`**, and the build and tests have run green **or** the comment says exactly why they could not run (see "Tests and review are one step" below). Waiting for the QA check in the UI ([chapter 07](07-qa-check-in-the-ui.md)). | The agent or developer moves it **right after the merge** and sets the label `qa-pending` |
| **Done** | **Done** | The QA check passed (label `qa-passed`) and the plan row Evidence / Test Plan status are updated. | Moved by the tester or the owner after the QA verdict |

Order (owner decision 2026-10-26): tests (if you can run them) -> PR -> **merge into `main`** -> In Review + `qa-pending` -> QA check, whose **line 1 is the local test run** -> Done. An issue never skips In Review.
**Sync with `main` right before the merge** (owner decision 2026-10-31): other sessions merge all the time, so just before you merge, fetch and merge the newest `main` into your branch (`git fetch origin` then `git merge origin/main`; in an app worktree use the `sync_with_base_branch` tool), fix every conflict, run the affected tests again, push, and only then merge the PR. Never merge on the strength of an earlier sync, and never resolve a conflict by dropping the other side's change: keep both, or ask the person who made it. If `main` moves again while you were fixing conflicts, repeat the sync.
A task whose *Done when* needs the owner's or a member's approval of a document gets that approval as the review of the PR; the merge follows the approval.
If the QA check fails, the issue goes **back to To Do** with the label `qa-failed` and the defects listed in a comment (owner decision 2026-10-26); it keeps its assignee and its QA comments. Whoever takes it up again moves it to In Progress (section 2), the fix reaches `main` through a new branch and PR (fix forward), then it goes to In Review again.

**The author does not wait for QA** (owner decision 2026-10-27). In Review is the hand-over: after the merge the author moves the issue to In Review with `qa-pending` and **goes on to the next task**. The QA check and the Done are done by someone else, at the end of the sprint if need be, once all sprint tasks are In Review. The author's only duty at the hand-over is an honest test note in the move comment: **"Tests: passed"** with the commands and counts, or **"Tests: not run / not done"** with the exact commands and the reason (no SQL Server, no browser, needs a real deploy, ...). The author never moves an issue to Done, not even when every test passed, and never keeps a task open waiting for a reviewer.

**Move to In Review (conditional done)** only when **all** are true:

- every item in *Done when* is met (check them one by one in your closing comment);
- the build and **all** tests passed, including the new tests the issue asks for (chapter 01, "Definition of done"), **or** they could not be run in your session (for example a cloud session without the .NET SDK or SQL Server): then the comment says so, lists the commands that were not run, and the test run becomes line 1 of the QA checklist (README.md "Local tests"). **Tests and review are one step for now** (owner decision 2026-10-26, no CI gate exists yet, #7): a person runs the tests and the UI checks together; Done needs both green;
- the issue carries the **QA checklist comment and a Tests paragraph** (how to test by README references; commands run or not run) - on the first move and on every re-entry after a failed QA, re-checked and updated as in [chapter 07](07-qa-check-in-the-ui.md) section 1a;
- changes are committed, pushed, a PR is opened and **merged into `main`** (the merge is the step right before In Review; promotion to `staging`/`demo` stays a separate decision);
- the six artefacts of rule 22 are updated (chapter 06): memory/guideline, plan file, Supportability Matrix, Instructions (only if a rule changed), CHANGELOG, commit.

Then:

1. **Comment** with: what changed, files/areas touched, tests added, tests run and **not** run (and why), commit hash or PR link, evidence for each *Done when* item, Supportability Matrix rows added, guideline entries added, open items for the owner. **Also post the QA checklist and the "QA checklist - author results" comments** ([chapter 07](07-qa-check-in-the-ui.md) sections 1a and 1b): every test or check you did not run (SQL Server tests, HTTP smoke tests, browser check) is an unchecked line there, `not done - <reason>`; a sentence in the move comment is not enough, because the next person may only have Jira.
2. **Transition to In Review** with `transitionJiraIssue` right after the merge, add the label `qa-pending` and add the merge commit to the comment; the QA check ([chapter 07](07-qa-check-in-the-ui.md)) then decides: `qa-passed` -> **Done**, `qa-failed` -> back to To Do.
3. **Parent rules** (apply to Done, not In Review; Done means the QA check passed): a Story with Sub-tasks is Done only when all its Sub-tasks are Done; an Epic only when all child issues are Done. When you close the last open child, check the parent and close it too if its own "Done when" is met.
4. **Clean up the branch.** When the work is merged into its target (this happens before In Review) (`main`; promotion to `staging` and `demo` is a separate merge the user directs, because those pushes deploy), **delete the working branch** locally (`git branch -d <name>`) and on the remote if it was pushed (`git push origin --delete <name>`); use `-d`, which refuses unmerged work, and never delete `main`, `staging`, `demo` or someone else's branch. Mention the deletion in the Jira comment. Then run `git branch --merged` to see leftovers and report them. **Since 2026-10-26 the repository deletes the head branch automatically when its pull request is merged** (GitHub setting "Automatically delete head branches"); a cloud session cannot delete remote branches, so it deletes only its local branch and checks with `git fetch --prune` that the remote one is gone.
5. **Update the guideline** if the task produced a durable lesson, decision, helper or pattern (chapter 06).
6. **Finish, then stop** (rule 16): propose a short list of next tasks (mention batchable ones) and wait for the user's choice.

## 4a. Branch hygiene and long-lived branches (owner decision 2026-10-27)

Run the branch audit ([chapter 05](05-environment-and-commands.md)) at the start of a session and once a week, and compare it with Jira:

- A branch **ahead of `main` whose issue is In Review or Done** is a violation: the work must be on `main`. Merge it now: open a PR, resolve the conflicts, run the local gates, merge; GitHub deletes the head branch. Do the same for a branch whose issue key you cannot find, but ask the owner first if it is not your own work.
- **Merging a branch that is far behind `main`:** make a working branch from `origin/main`, merge the old branch into it, resolve conflicts by keeping both sides when both only added lines (`.gitignore`, `.resx`, guideline lists, learnings log), then re-check what auto-merged: EF migration order and the model snapshot (drift gate must be clean), `Program.cs`, env key parity in all six files, no duplicate resource keys. Never resolve a snapshot or a generated file conflict by guessing: regenerate it. Plan rows are one file each, so a plan conflict is a real conflict on the same row: keep both sides' facts.
- A branch with **0 commits ahead** of `main` is finished: delete it (never `main`, `staging`, `demo`; a branch named `fix` blocks every `fix/...` name, so delete such stale names).
- **A cloud session started from an old brief must restart from `main`.** If its issue was already merged, it does not recreate the old branch name or redo the work: it reads the issue comments and the merged PR first (the Jira step 0 check) and continues from `main`. A branch that reappears after its PR was merged is audited like any other.
- **Pull `main` before you restart or resume a task after a pause** (owner decision 2026-10-29; it applies to every agent and person, in any session, local or cloud): run `git fetch` and fast-forward `main` (`git pull --ff-only origin main`) before you read the issue, create or reuse a branch, or continue old work. Other people merge while you are away (plan rows, guideline, migrations). If you resume on an existing branch, merge the fresh `main` into it first and re-read the issue comments and the plan row, then continue. Never start from a stale checkout.
- **In Review never blocks you** (owner decision 2026-10-29): when your task is In Review (merged, waiting for the QA check, or PR waiting for approval) do not stop and wait. Move on to the next approved task or the next task of the batch and keep working. While the sprint is open, In Review counts as done for planning: a task whose dependencies are merged into `main` (they are In Review) may start right after that merge, without waiting for the QA verdict (note the dependency's state in your plan comment, and if the QA later fails and the dependency returns to To Do, fix forward and tell the dependent task's owner). Only the final Done stays tied to the QA verdict (next rule) and is settled when the sprint closes.
- **A delayed merge is a defect (owner decision 2026-11-04: "this delayed merges make the team unstable"): once the quick gates pass, merge in the same turn. Tests the session cannot run (SQL Server, browser) never hold a merge; they go on the In Review QA checklist and are done after it.** **Merging your pull request into `main` needs no extra approval** (owner decision 2026-10-29): once the task is approved and started, the author (person or agent) merges its own PR into `main` as soon as the PR checks are green or their gaps are listed in the PR, then moves the issue to In Review; do not stop to ask for a merge approval, not even as the closing question of a report (owner decision 2026-10-31, SCRUM-475: asking "merge it?" for an ordinary working-branch PR is a violation of this rule; just merge, or report that the tool blocked it). This covers only working branches into `main`. It does not cover force pushes, deleting branches other than your own merged one, rewriting history, pushing or merging to `staging`/`demo` (these deploy), changing secrets or settings, or a PR whose checks fail. A permission prompt of the tool is a separate matter: if the tool itself blocks the merge, say so in the report and leave the PR open; never work around it. The tool's permission classifier can deny the merge call ("Merge Without Review") even though this rule allows it; the owner's chat message "merge it" lifts that for the PR named, and the person who runs the agents can allow the call for good with a permission rule for `gh api -X PUT repos/atapems-tech/PEMS/pulls/*/merge*` in their own Claude settings (an agent must not edit its own permissions). The human review happens after In Review, not before the merge. If GitHub times out (`TLS handshake timeout`), retry the merge several times before reporting.
- **Dependencies: resolve, wait or split - never stop** (owner decision 2026-10-29). Before and during the work read the `depends` field of the plan row and the state of each dependency in Jira, then act by its state:
  - *Merged or In Review* (merged into `main`): the dependency is satisfied; start (see the previous rule) and record the dependency's state in your plan comment.
  - *To Do and yours, or unassigned*: start it first. Add it to the current batch, move it to In Progress and assign it to the person doing the work in the same step (section 1, step 5), do it, merge it, then continue with the task that needed it. The ownership check (5a) still applies to anything with another assignee.
  - *To Do or In Progress and assigned to someone else*: do not touch it and do not wait idle. Comment on the dependency (mention the assignee) that your task needs it, work on the part that does not need it or on another task, and check its state again at the next pause (together with pulling `main`).
  - *Blocked by a loop or by something that cannot be done now* (circular dependency, a dependency that waits for a decision, a missing external input, a held task): do every part that can be done, deliver and merge it, and create a **follow-up task** for the part that needs the blocked dependency. Before creating it apply rule 28 (study existing tasks; modify a fitting one instead of adding a duplicate). The follow-up names the blocker, the finished part and the exact remaining scope, depends on the blocker, and is created unassigned and outside any sprint. Report the split in the Jira comment of the original task and keep moving to the next task.
  A task is closed against its own *Done when*; a dependency split off this way must be reflected in the *Done when* of both tasks (edit the plan row, not only the Jira text). Keep the plan rows' `depends` fields true (`plan_sync.py check` rejects a milestone conflict).
- **No issue without an epic** (owner decision 2026-10-29): every Jira issue (task, story, bug, follow-up, split-off part of a blocked dependency) is created **with its parent Epic** (`parent` field of `createJiraIssue`). Pick the epic that matches the plan row's area; study the existing epics first (rule 28) and, if none fits, create the epic first (an epic itself is the only issue without a parent), then the issue under it. The plan row names the epic in its `group` field and `plan_sync.py new` / the export must use it. Do not create an issue and promise to attach an epic later. When you touch an existing issue that has no epic, attach it in the same step and mention it in the comment.
- **When only checking is left, move to In Review - do not stay In Progress** (owner decision 2026-10-29). In Progress means implementable work is still open. Do everything that is not checking, testing or reviewing first (code, docs, workflows, Jira and plan updates, merges). When all of that is merged and what remains is verification - local or CI test runs you could not do, live checks on a server, a browser or phone check, a reviewer's look, a person's approval - the issue moves to **In Review** with `qa-pending`, and every remaining check becomes an **unchecked line of the QA checklist** with the exact command or steps (chapter 07, section 1a). Hold-ups that need access only another person has (Plesk, DNS, Jira admin, secrets) are not a reason to keep the issue In Progress: if the step is a check, it is a QA line; if it is a deliverable action, create an unassigned follow-up under its epic (rule: no issue without an epic) and list it as a QA line of the original issue. While the sprint is open nobody sits idle on a blocked issue: report the state in the Jira comment and take the next task.
- **No direct Done:** an issue never goes from To Do or In Progress to Done. The only way to Done is In Review, then the QA verdict. A parent whose children are all Done may be closed by the owner; say so in its comment. (Enforcement is a Jira workflow setting, see chapter 06 open points.)

## 5. When you cannot finish

- Do **not** move the issue to In Review or Done. Leave it In Progress.
- Comment: what is done, what is left, what blocks.
- Tell the user in the session. If it should wait for a decision, propose Hold (On Hold) rather than silently leaving it.

## 6. Never

- Never move an issue to Done from To Do or In Progress; Done is reached only from In Review after the QA verdict (section 4a).
- Never mark In Review because the session is ending or the code "looks finished" unless the tests passed or the comment states exactly which tests could not run and why. Never mark In Review before the PR is merged into `main`, and never mark Done before the tests are green and the QA check passed.
- Never delete, overwrite or collapse a QA checklist or QA result comment, not even after Done; they stay on the issue as organisational knowledge ([chapter 07](07-qa-check-in-the-ui.md) section 7).
- Never leave an issue In Progress / In Review without an assignee.
- Never change statuses of issues you were not asked to work on (parent rules and approved batches excepted).
- Never set "Confirmed by PM" yourself except to record a decision the owner just gave (rule 19).
- Never claim a feature externally (sales, website, demo) that is not Done with evidence (rule 13).
- Never commit to `main`/`staging`/`demo` directly or leave merged working branches behind; changes reach them only by merging a working branch (the user decides the merge target and whether a PR is needed); never skip hooks; never force-push shared branches. A push to `staging` or `demo` deploys an environment: do it only when the user asks for that deploy.

## 7. Working with the user

- The user talks Persian; reply in the user's language in chat. Code, comments in infrastructure code, commits, Jira, docs: English. Domain entity XML comments may be Persian (existing convention).
- Finish what you start; report honestly: failing tests, skipped steps and unverified claims are stated, not hidden.
- For hard-to-reverse or outward-facing actions (push, deploy, delete, Jira bulk changes, publishing) confirm first unless the user already authorised that exact action.
